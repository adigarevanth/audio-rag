Audio RAG

Hybrid Search Over Audio Transcripts

Keyword + Semantic Search  |  Speaker Diarization  |  Reciprocal Rank Fusion

1

The Problem

  • Audio recordings contain valuable information but are unsearchable by default
  • Transcripts alone aren't enough — users search using their own words, not the exact words spoken
  • Need to know who said what and when — not just find matching text
  • Keyword search fails when query wording differs from transcript wording

Challenge: Build a hybrid search system that handles both exact keyword queries and natural-language meaning queries across multi-speaker audio recordings.

2

Our Solution

A four-stage pipeline: Transcribe → Diarize → Index → Search

Pipeline

  • Transcribe audio with word-level timestamps
  • Identify speakers using voice fingerprinting
  • Align words to speakers, chunk by speaker turn
  • Embed + Index into Postgres with pgvector
  • Search with keyword + semantic + RRF fusion

Architecture

Audio Files (5 × 10 min, 2 speakers each) │ ▼ faster-whisper (local) → words + timestamps pyannote.audio (local) → speaker segments │ ▼ Alignment + Chunking → speaker turns │ ▼ all-MiniLM-L6-v2 (local) → 384-dim embeddings Postgres tsvector → full-text tokens │ ▼ Postgres + pgvector (Docker) → unified storage │ ▼ Hybrid Search (RRF) → ranked results

Fully local. No paid APIs. Reproducible from a single docker compose up.

Why Hybrid Search?

Keyword search alone fails 61% of the time.

User searches:

"what caused the fall of Constantinople"

Transcript says:

"armies from mostly France sack Constantinople and dismember the empire"

No exact word overlap → keyword returns NOTHING

Semantic search:

Understands "caused the fall" ≈ "sack and dismember"

Finds the right chunk ✓

Hybrid (RRF):

Boosts results that match on both keywords and meaning

Best ranking ✓

Key Observations

  1. Keyword search alone is insufficient — returned NO RESULTS for 22 out of 35 queries (61%)
  2. Semantic search is the primary driver of recall — hybrid and semantic have identical recall (0.957)
  3. Hybrid's advantage is ranking (MRR) — RRF boosts results matching both modalities, improving MRR by 11% over semantic-only (0.858 vs 0.772)
  4. Multi-result queries are harder — recall drops to 0.5 at k=5 when expecting 2+ results
  5. One persistent failure — "condolence cards" query fails due to chunking boundary, not search
10

Limitations & Future Work

Limitations

  • 36 queries / single annotator — directional, not statistically robust
  • Precision@k structurally low with 1-2 expected results per query
  • Transcription errors propagate to both search modalities
  • CPU-only: diarization takes ~15 min per 10-min file

Future Improvements

  • Overlapping chunks for better boundary coverage
  • Cross-encoder re-ranking for higher precision
  • GPU acceleration for real-time indexing
  • User feedback loop to improve ranking
  • Multiple annotators for golden dataset
